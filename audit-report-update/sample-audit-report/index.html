1. Summary

Result: The homepage does not meet WCAG 2.2 Level AA. People who use a keyboard or a screen reader cannot use the navigation, add products or send the order form. Many visitors with low vision will struggle to read the text.

I found 18 issues. Three of them stop some visitors from completing key tasks and should be fixed first.

  • 3Critical
  • 6Serious
  • 7Moderate
  • 2Minor

Top 3 priorities

  1. Make every menu link and button work with a keyboard (issues 1 and 2). Right now they only respond to a mouse click.
  2. Add labels to the order form (issue 3) so screen reader users know what each field is for.
  3. Fix the colour contrast (issue 4). Most text on the page is far too faint, as low as 1.6:1 against a minimum of 4.5:1.

Most fixes are small changes to HTML and CSS, and the design can stay the same. I estimate 6–8 hours to fix everything in this report (see the fix plan).

2. Scope and method

In scope: the homepage, including the header and navigation, mobile menu, product list, reviews carousel, order form and footer, on desktop and mobile screen sizes.

How I tested:

  • Automated scans with Google Lighthouse (mobile) and WebAIM's WAVE tool
  • Keyboard-only testing: using the whole page with Tab, Shift+Tab, Enter, Space and Esc
  • Manual code review of the HTML, CSS and JavaScript against each WCAG 2.2 Level A and AA success criterion
  • Colour contrast measurements for every text and border colour
  • Zoom and mobile checks at 200% zoom and a 390px-wide phone screen

5. Findings and fixes

1. Navigation and mobile menu don't work with a keyboard

Critical
WCAG
2.1.1 Keyboard (A), 4.1.2 Name, Role, Value (A)
Where
Header: "Menu", "Reviews", "Order" links and the ☰ menu icon
Who is affected
Keyboard users, screen reader users, people using switch devices or voice control

Problem: The menu items are <div> elements with a click handler. They can't be reached with Tab and aren't announced as links. In keyboard testing, pressing Tab reached only the three form fields. No link or button on the page could be reached. The ☰ icon has no name, so a screen reader can't describe it.

Current code

<div class="menu-btn" onclick="...">&#9776;</div>
<div onclick="location.href='#menu'">Menu</div>

Recommended fix

<nav aria-label="Main">
  <button class="menu-toggle" aria-expanded="false" aria-controls="main-menu">Menu</button>
  <ul id="main-menu">
    <li><a href="#menu">Our menu</a></li> ...
  </ul>
</nav>

Update aria-expanded when the menu opens and closes, and let Esc close it.

2. "Add" and "Send" buttons aren't real buttons

Critical
WCAG
2.1.1 Keyboard (A), 4.1.2 Name, Role, Value (A)
Where
The three "Add" buttons in the menu section and the "Send" button on the order form
Who is affected
Keyboard and screen reader users

Problem: These are styled <div>s, so keyboard users can't add products or send an order. The three "Add" buttons also sound identical to a screen reader, which can't tell which product each one adds.

Recommended fix

<button class="btn">Add<span class="visually-hidden"> Coconut Loaf to order</span></button>
<button class="btn" type="submit">Send order</button>

3. Order form fields have no labels

Critical
WCAG
1.3.1 Info and Relationships (A), 3.3.2 Labels or Instructions (A), 4.1.2 Name, Role, Value (A)
Where
Name, Phone and "What would you like?" fields
Who is affected
Screen reader users, people with memory or attention difficulties

Problem: The fields use placeholder text instead of labels. The hint disappears as soon as someone starts typing, is very faint, and isn't reliably announced by screen readers. Required fields aren't marked.

Recommended fix

<label for="name">Name *</label>
<input id="name" name="name" autocomplete="name" required aria-describedby="name-error">
<p class="field-error" id="name-error"></p>

4. Text colour contrast is too low across the page

Serious
WCAG
1.4.3 Contrast (Minimum) (AA)
Where
Body text, section headings, logo, navigation, buttons, prices, footer, hero headline
Who is affected
People with low vision or colour blindness, older visitors, anyone on a phone in sunlight

Problem: WAVE found 26 contrast errors. Normal text needs at least 4.5:1, and the page goes as low as 1.6:1. The white hero headline sits directly on a busy photo with no overlay. See section 6 for every colour pair measured.

Fix: Use dark text (for example #1f1a10) on the yellow brand colour instead of white, darken grey text to #333, darken the price colour to #6b4e00, and add a dark overlay behind the hero headline. The bakery keeps its yellow brand colour.

5. Images have no alt text

Serious
WCAG
1.1.1 Non-text Content (A)
Where
Logo image and three product photos (4 images)
Who is affected
Screen reader users; also anyone whose images fail to load

Problem: Without an alt attribute, screen readers may read out the image's file name or web address instead.

Recommended fix

<img src="coconut-loaf.jpg" alt="A sliced golden loaf of bread on a wooden board">
<!-- Decorative logo shape next to the business name: -->
<svg aria-hidden="true" focusable="false">...</svg>

6. Keyboard focus outline has been removed

Serious
WCAG
2.4.7 Focus Visible (AA)
Where
Whole site (CSS rule *:focus { outline: none; })
Who is affected
Keyboard users, who can't see where they are on the page

Recommended fix

/* Remove: *:focus { outline: none; } */
:focus-visible { outline: 3px solid #0b57d0; outline-offset: 3px; }

7. Reviews rotate automatically with no way to pause

Serious
WCAG
2.2.2 Pause, Stop, Hide (A)
Where
"What people say" section
Who is affected
Slow readers, people with attention or cognitive difficulties, screen reader users

Problem: A new review appears every 2.5 seconds, which is too fast for many people to read, and nothing stops it.

Fix: Add Pause, Previous and Next buttons, slow the rotation to at least 6 seconds, and stop it automatically for visitors who have turned on "reduce motion" in their device settings.

8. Form errors use colour only and don't explain the problem

Serious
WCAG
1.4.1 Use of Color (A), 3.3.1 Error Identification (A), 3.3.3 Error Suggestion (AA)
Where
Order form
Who is affected
Colour-blind users, screen reader users, everyone

Problem: When a field is empty, the page only turns its border red and shows the single word "Error." It doesn't say which field is wrong or what to do, and screen readers don't announce it.

Fix: Show a specific message under each field (for example, "Enter your phone number."), connect it with aria-describedby, mark the field aria-invalid="true", and move focus to an error summary at the top of the form.

9. Zooming is disabled on phones

Serious
WCAG
1.4.4 Resize Text (AA)
Where
Viewport meta tag in the page head
Who is affected
People with low vision on mobile devices

Recommended fix

<!-- Before -->
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no">
<!-- After -->
<meta name="viewport" content="width=device-width, initial-scale=1">

Also raise the base text size from 13px to at least 16px.

10. Page has no heading structure

Moderate
WCAG
1.3.1 Info and Relationships (A), 2.4.6 Headings and Labels (AA)
Where
Hero text and section titles ("Our Menu", "What people say", "Order ahead")
Who is affected
Screen reader users, who often jump between headings to find content

Problem: The page has no <h1>. The section titles are styled <div>s, and the product names jump straight to <h4>.

Fix: Make the hero text the <h1>, the section titles <h2>, and the product names <h3>.

11. No page landmarks or "skip to content" link

Moderate
WCAG
1.3.1 Info and Relationships (A), 2.4.1 Bypass Blocks (A)
Where
Whole page
Who is affected
Keyboard and screen reader users

Fix: Wrap the page in <header>, <nav>, <main> and <footer>, and add a "Skip to main content" link as the first item on the page. It can stay hidden until it receives keyboard focus.

12. Fake links and "click here" link text

Moderate
WCAG
2.4.4 Link Purpose (A), 2.1.1 Keyboard (A)
Where
"click here" for catering orders; Facebook and Instagram in the footer
Who is affected
Keyboard users, and screen reader users who browse a list of links

Problem: These look like links but are <span>s, so they can't be reached by keyboard. The footer ones don't go anywhere. "Click here" means nothing when read out of context.

Recommended fix

<a href="#order">Ask us about catering orders</a>
<a href="https://facebook.com/seabreezebakery">Facebook</a>

13. Form field borders are nearly invisible

Moderate
WCAG
1.4.11 Non-text Contrast (AA)
Where
All order form fields
Who is affected
People with low vision, who may not see where to type

Problem: The #f0f0f0 border on white has a contrast of 1.14:1, and form controls need at least 3:1.

Fix: Use a 2px #767676 border (4.54:1).

14. Form fields don't support autofill

Moderate
WCAG
1.3.5 Identify Input Purpose (AA)
Where
Name and Phone fields
Who is affected
People with motor or memory difficulties; also faster for everyone

Fix: Add autocomplete="name" and type="tel" autocomplete="tel" so browsers can fill these in automatically.

15. Page language is not set

Moderate
WCAG
3.1.1 Language of Page (A)
Where
<html> tag
Who is affected
Screen reader users, whose software may read the text with the wrong accent or pronunciation

Fix: <html lang="en">

16. Page title isn't descriptive

Moderate
WCAG
2.4.2 Page Titled (A)
Where
<title>Home</title>
Who is affected
Screen reader users, anyone with several tabs open, and search engines

Fix: <title>Seabreeze Bakery – Fresh bread baked every morning</title>

17. Pop-up alerts interrupt visitors

Minor
WCAG
4.1.3 Status Messages (AA), best practice
Where
"Added!" and "Sent!" browser pop-ups
Who is affected
Everyone, especially screen reader users

Fix: Replace alert() with a message on the page inside <p role="status">, for example "Coconut Loaf added to your order." Screen readers announce it without interrupting the visitor.

18. Small click and tap targets

Minor
WCAG
2.5.8 Target Size (Minimum) (AA), best practice
Where
Navigation items and footer links
Who is affected
People with motor difficulties and touchscreen users

Fix: Add padding so every link and button is at least 24×24px. 44×44px is better for touchscreens.

7. Recommended fix plan

  1. Phase 1: Critical (about 2–3 hours). Issues 1–3. Rebuild the menu, buttons and form controls with proper HTML. After this phase, everyone can navigate and order.
  2. Phase 2: Serious (about 2–3 hours). Issues 4–9. New accessible colour values, alt text, focus styles, carousel controls, clear error messages, and re-enabling zoom.
  3. Phase 3: Moderate and minor (about 1.5–2 hours). Issues 10–18. Headings, landmarks, skip link, link text, borders, autofill, language, title, status messages and target sizes.
  4. Re-test (included). Run Lighthouse, WAVE, keyboard and contrast checks again and send a short before-and-after summary.

These fixes were applied to the demo page, and the results were: Lighthouse 50 → 100, WAVE errors 8 → 0, contrast errors 26 → 0. See the full before-and-after case study.

8. Limitations

  • This audit covers one page. Other pages, such as a checkout or contact page, may have different issues.
  • Automated tools catch only some accessibility problems, so this report combines them with manual testing. Testing with real users with disabilities is the best way to confirm a site works for everyone.
  • This report measures the page against the WCAG 2.2 Level AA guidelines. It is not legal advice and does not certify legal compliance.
